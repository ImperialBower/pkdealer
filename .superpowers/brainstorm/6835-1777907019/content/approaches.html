Three Architectural Approaches

All three use a shared-crate workspace. They differ in how much the shared layer does.

A

Layered Workspace — Explicit wiring

Extract infrastructure into cardgame-infra. Each game implements CardGame trait manually and wires it to a service binary by hand.

cardgame-infra ← auth, events, seat mgmt, base gRPC
cardgame-proto ← shared base proto
├── pkcore (ext) + pkdealer-proto + pkdealer-service
├── bjcore + bj-proto + bj-service
├── gofishcore + gofish-proto + gofish-service
└── bridgecore + bridge-proto + bridge-service

Pros

  • Crystal-clear, no magic
  • Each game fully independent
  • Easy to reason about

Cons

  • Most boilerplate per new game
  • Easy for wiring to diverge across games
B

Generic Server Shell — Compile-time parameterization ★ Recommended

The shared crate provides a GameServer<G: CardGame>. Each game just implements the trait and writes a ~20-line main.rs. No runtime overhead — Rust monomorphizes at compile time.

cardgame-core ← CardGame trait + GameServer<G> + infra
cardgame-proto ← shared base proto
├── pkcore (ext) + pkdealer-proto + pkdealer/main.rs (10 lines)
├── bjcore + bj-proto + bj/main.rs (10 lines)
├── gofishcore + gofish-proto + gofish/main.rs (10 lines)
└── bridgecore + bridge-proto + bridge/main.rs (10 lines)

Pros

  • Very low boilerplate per new game
  • Trait enforces consistency
  • Zero runtime cost (monomorphized)
  • Natural Rust idiom

Cons

  • Trait design must accommodate all games upfront
  • More complex shared crate to understand initially
C

Macro-Assisted — Derive the service glue

Approach B + a proc-macro #[derive(GameService)] that generates the gRPC service impl and proto glue from the CardGame impl. Absolute minimum per-game code.

cardgame-core ← CardGame trait + GameServer<G> + infra
cardgame-macros ← #[derive(GameService)] proc-macro
cardgame-proto ← shared base proto
├── pkcore + pkdealer-proto
│ └── #[derive(GameService)] struct PokerGame; (3 lines)
├── bjcore + bj-proto
│ └── #[derive(GameService)] struct BlackjackGame;
└── ...

Pros

  • Absolute minimum per-game boilerplate
  • Strongly enforced structure

Cons

  • Proc-macros are complex to write and maintain
  • Harder to debug ("magic" errors)
  • Likely premature at this stage

My recommendation

Start with B. The generic GameServer<G: CardGame> approach gives you the structural discipline of a well-defined trait and near-zero per-game overhead — without the maintenance burden of proc-macros. C can be added later once the trait stabilizes across 2–3 games.
