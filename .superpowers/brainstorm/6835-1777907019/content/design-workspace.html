Design: Workspace Structure

Section 1 of 5 — How the crates are laid out

Proposed workspace layout

cardgame/ ← repo root (renamed or new repo)
├── Cargo.toml (workspace)
├── proto/
│ ├── cardgame_base.proto ← shared RPCs & messages
│ ├── poker.proto ← poker-specific extensions
│ ├── blackjack.proto ← blackjack extensions
│ ├── gofish.proto ← go fish extensions
│ └── bridge.proto ← bridge extensions
├── crates/
│ ├── cardgame_core/ ← CardGame trait + GameServer<G> + infra
│ ├── cardgame_proto/ ← compiled base proto + re-exports
│ ├── poker_proto/ ← compiled poker proto
│ ├── poker_service/ ← binary: GameServer<PokerGame>
│ ├── blackjack_proto/
│ ├── blackjack_service/ ← binary: GameServer<BlackjackGame>
│ ├── gofish_proto/
│ ├── gofish_service/ ← binary: GameServer<GoFishGame>
│ ├── bridge_proto/
│ └── bridge_service/ ← binary: GameServer<BridgeGame>
└── docs/

Colour key

■ Shared layer (written once) ■ Per-game proto + engine adapter ■ Per-game service binary (~20 lines)

Key principle

Game engines (pkcore, future bjcore, etc.) live outside this workspace as external crate dependencies. Each *_service binary is a thin adapter: it depends on cardgame_core + its engine crate and calls GameServer::run(MyGame::new()).

What cardgame_core contains

  • CardGame trait — the central contract every game engine adapter must implement
  • GameServer<G: CardGame> — generic gRPC server that delegates to any CardGame
  • Auth layer — UUID token management, seat ↔ token maps
  • CardVisibility — Hidden / Player(seat) / Spectator (already in pkdealer)
  • Event broadcasting — tokio broadcast channel + per-subscriber filtering
  • Seat management — generic N-seat table, seating/removal logic
  • Error types — shared gRPC status codes and domain errors
