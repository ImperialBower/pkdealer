Design: The CardGame Trait

Section 2 of 5 — The central contract every game engine adapter must implement

Trait definition (in cardgame_core)

pub trait CardGame: Send + Sync + 'static {
  // ── Associated types ──────────────────────────
  type Action: Send + Sync + fmt::Debug;
  type Config: Send + Sync + Default;
  type Error: error::Error + Send + Sync + Into<tonic::Status>;

  // ── Lifecycle ─────────────────────────────────
  fn new(config: Self::Config) -> Result<Self, Self::Error> where Self: Sized;
  fn start_round(&mut self) -> Result<(), Self::Error>;
  fn end_round(&mut self) -> Result<RoundResult, Self::Error>;

  // ── Player actions ────────────────────────────
  fn apply_action(&mut self, seat: u8, action: Self::Action)
    -> Result<ActionOutcome, Self::Error>;
  fn valid_actions(&self, seat: u8) -> Vec<Self::Action>;

  // ── State queries (feed the base proto) ───────
  fn next_to_act(&self) -> Option<u8>;
  fn is_round_in_progress(&self) -> bool;
  fn seat_count(&self) -> u8;
  fn player_cards(&self, seat: u8, vis: CardVisibility) -> Vec<String>;
  fn shared_cards(&self) -> Vec<String>; // empty for non-community-card games
  fn chips(&self, seat: u8) -> Option<u64>; // None for chipless games
  fn pot(&self) -> u64;
  fn phase_name(&self) -> String; // "Preflop" / "Bidding" / "Deal" / …
  fn event_log(&self) -> Vec<String>;
}

How each game maps its engine to the trait

Poker (existing pkcore)
Action = PlayerAction
Config = TableConfig
phase_name → Street
shared_cards → board
chips → stack
pot → pkcore pot
Blackjack (new bjcore)
Action = Hit|Stand|Double|Split
Config = DealerRules
phase_name → "PlayerTurn" | "DealerTurn"
shared_cards → dealer hand
chips → bet + stack
pot → total wagered
Go Fish (new gofishcore)
Action = Ask(rank) | DrawFromPond
Config = PlayerCount
phase_name → "Ask" | "Draw"
shared_cards → [] (none)
chips → None (chipless)
pot → 0
Bridge (new bridgecore)
Action = Bid(contract) | Play(card) | Pass
Config = BiddingSystem
phase_name → "Bidding" | "Play" | "Scoring"
shared_cards → dummy hand (after opening lead)
chips → None
pot → 0

Why associated types over generic parameters

Using type Action (associated type) rather than CardGame<A, C, E> (generic parameters) means you never write GameServer<G, G::Action, G::Config> — the compiler resolves everything through G alone. Cleaner bounds, cleaner error messages.
