Design: Hybrid Proto Structure

Section 4 of 5 — Shared base proto + per-game extension protos

cardgame_base.proto — written once, imported by all games

package cardgame.base.v1;

// Shared RPCs every game service exposes
service CardGameBase {
  rpc Ping (PingRequest) returns (PingReply);
  rpc SeatPlayer (SeatPlayerRequest) returns (SeatPlayerResponse);
  rpc SeatPlayerAt (SeatPlayerAtRequest) returns (SeatPlayerAtResponse);
  rpc RemovePlayer (RemovePlayerRequest) returns (RemovePlayerResponse);
  rpc GetStatus (GetStatusRequest) returns (GetStatusResponse);
  rpc GetChips (GetChipsRequest) returns (GetChipsResponse);
  rpc GetPot (GetPotRequest) returns (GetPotResponse);
  rpc GetEventLog (GetEventLogRequest) returns (GetEventLogResponse);
  rpc GetTableConfig (GetTableConfigRequest) returns (GetTableConfigResponse);
  rpc StreamEvents (StreamEventsRequest) returns (stream TableEvent);
}

// Shared messages
message SeatInfo { uint32 seat = 1; string name = 2; repeated string cards = 3;
  uint64 chips = 4; string state = 5; }
message TableEvent { string type = 1; uint64 timestamp_ms = 2; string payload_json = 3; }
message RoundResult { repeated WinnerInfo winners = 1; string description = 2; }
message WinnerInfo { uint32 seat = 1; string name = 2; uint64 amount = 3; string hand = 4; }

Composition vs. inheritance

Protobuf has no service inheritance. Instead, each game's service includes all the base RPCs by redeclaring them (the GameServer<G> implements both). This is intentional: gRPC reflection and tooling work cleanly, and clients only need one stub. The alternative (two separate service stubs per game) would require clients to manage two connections.

Versioning strategy

cardgame_base.proto is versioned independently (v1, v2…). Per-game protos pin a specific base version in their import path, so a base change doesn't silently break all games at once.
